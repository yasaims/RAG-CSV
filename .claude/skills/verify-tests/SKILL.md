# Verify Tests

実装者(自分自身を含む)がテストを「通した」と主張していることを、鵜呑みにせずに独立して検証するためのスキル。
このスキルの目的は「テストが緑になったこと」の確認ではなく、「テストが正しい理由で緑になったこと」の確認。

## 基本方針

- 検証者は実装者から独立した視点を持つこと。実装の意図を推測して好意的に解釈しない。
- 「グリーンにする」ことと「正しく動く」ことは別物。グリーン化のために不正な近道が使われていないかを常に疑う。
- 証拠(コマンドの実行結果、diffの該当箇所)を示さない結論は無効。「たぶん大丈夫」は禁止。

## 検証手順

### 1. テストスイートを実行する

```bash
pytest -q
```

- 失敗があれば、その時点でFAILとして報告してよい(以降の手順は不要)。
- 全て通った場合のみ次のステップへ進む。
- カバレッジが設定されていれば `pytest --cov` も併用し、新規/変更コードがテストで実際に実行されているかを確認する。
- テストが1件も収集されていない(collected 0 items)場合は要注意。それ自体をFAIL理由として報告する。

### 2. 差分(diff)を読む

```bash
git diff HEAD~1        # 直前コミットとの差分、または
git diff main          # ベースブランチとの差分
git diff --stat         # まず変更範囲の概観を掴む
```

- 実装コードの変更とテストコードの変更の両方を必ず読む。テストの差分だけを見て終わらせない。
- 「要求されていた仕様」と「実際の差分の内容」を突き合わせる。仕様を満たさずにテストだけ帳尻を合わせていないか確認する。

### 3. テストが「通すためだけに」弱められていないかを確認する

`red-flags.md` に典型的なズルのパターン一覧がある。詳細な判定基準はそちらを参照しつつ、最低限以下をdiff上でチェックする:

- assert文の削除、または条件を緩めた変更(例: `==` を `>=` や `is not None` に変更するなど、意味的に検証が弱くなっている)
- `@pytest.mark.skip` / `@pytest.mark.xfail` / `pytest.skip()` の新規追加
- テスト対象コードではなくテスト側だけを書き換えて期待値を実際の(誤った)出力に合わせた形跡
- 例外を握りつぶす `try/except: pass` の追加
- 過剰なモック化により、検証したいロジック自体が実行されずバイパスされている
- ハードコードされた値を返すだけの実装(テストケースの入力値決め打ち)
- テストファイル自体の削除、またはテスト関数のリネームによる無効化(pytestに収集されなくなる)
- CIやpytest設定(`pytest.ini`, `pyproject.toml`, `conftest.py`)側でのフィルタ変更により、失敗するはずのテストが除外されていないか

疑わしい変更を見つけたら、該当のdiff箇所を引用し、なぜ問題かを具体的に説明する。

### 4. 証拠を添えてPASS/FAILを報告する

以下のフォーマットで報告する。

```
## 検証結果: PASS または FAIL

### 実行結果
- コマンド: pytest -q の実際の出力(件数・成否)を引用
- 収集されたテスト件数、失敗件数

### 差分の確認
- 変更ファイル一覧(git diff --stat の結果)
- 実装側の変更点の要約
- テスト側の変更点の要約

### 弱体化チェック
- 該当なし、または発見した問題点をdiffの引用付きで列挙

### 結論
- PASS: 仕様を満たし、かつテストが不正に弱められていないと判断した根拠
- FAIL: 具体的にどのテスト/どの変更が問題かを明記
```

## 注意事項

- 実行結果やdiffの引用を省略して結論だけ書かない。人間が後から検証結果を追試できる粒度で書くこと。
- グレーゾーンの変更(例: 妥当な理由がありそうな条件緩和)を見つけた場合は、断定せずに「要確認」として明示し、実装者に理由を確認するよう促す。
- 大規模な差分の場合は、まずファイル単位で怪しい箇所に当たりをつけてから深掘りする(`red-flags.md` のキーワードでgrepすると効率的)。
