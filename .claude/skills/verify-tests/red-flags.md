# テストを不正に「通す」典型的なパターン (Red Flags)

diffをレビューする際に、以下のキーワード/パターンで当たりをつけると効率的。

```bash
git diff | grep -nE "pytest\.(mark\.)?(skip|xfail)|@skip|assert True|except.*:\s*pass|# noqa|TODO|FIXME"
```

## 1. アサーションの弱体化・削除

- `assert result == expected` → `assert result is not None` のような、検証の粒度を落とす変更
- 複数あったassertのうち一部だけをコメントアウト/削除
- `assert result == expected` を `# assert result == expected` にしてしまう
- 浮動小数点比較で許容誤差(`pytest.approx`など)を不自然に緩める

## 2. スキップ・除外による無効化

- `@pytest.mark.skip(reason="...")` や `@pytest.mark.xfail` の新規追加
- `pytest.ini` / `pyproject.toml` の `testpaths` や `-k` フィルタ変更で特定テストを収集対象から除外
- `conftest.py` の `collect_ignore` にテストファイルを追加
- テスト関数名の先頭から `test_` を外す(pytestに収集されなくなる)、あるいはファイル名を `test_*.py` パターンから外す

## 3. テスト側の期待値を実装の(誤った)出力に合わせる

- 実装のロジックが仕様通りでないのに、テストのexpected値だけを実際の出力に書き換えてグリーンにする
- 本来テストすべき境界値・異常系のテストケース自体を削除する

## 4. 例外の握りつぶし

- `try: ... except Exception: pass` を追加してエラーが起きても素通りさせる
- ログに出すだけで再raiseしない例外処理を新規追加し、失敗を隠蔽する

## 5. モックの過剰使用

- 検証したい対象の関数・メソッド自体をモックしてしまい、実際のロジックが一度も実行されないままテストが通る
- 外部依存だけでなく、テスト対象のコアロジックまでモックで置き換えている

## 6. ハードコード・決め打ち

- テストの入力値をリテラルで検出し、その入力の時だけ正解を返す実装(汎用ロジックになっていない)
- 乱数や日時に依存する処理で、テスト実行時のみ固定値を返すような分岐をこっそり追加

## 7. カバレッジ上の見落とし

- 新規追加した分岐やエラーハンドリングが、どのテストケースからも実行されていない(カバレッジレポートで未到達)
- 「全テストパス」でも、実装の主要な変更部分がテストされていないケース

## 判定のスタンス

- 上記に該当する変更を見つけたら即座にFAILとするのではなく、まずdiffを引用して「なぜ問題なのか」を説明できるようにする。
- 正当な理由がある変更(例: 元々のテストが誤っていて、issueやコミットメッセージで明確に説明されている修正)もあり得るため、文脈(コミットメッセージ、PR説明、issue番号)も合わせて確認する。
- 文脈が確認できず判断がつかない場合は「要確認」として実装者に確認を求める。
